# 6.4 大数据

> **考纲对应**：大数据 第 1~4 条——理解基本概念、结构类型与核心特征；了解时代背景、应用场景与发展趋势；了解系统架构及获取、存储、管理方面的技术架构；了解与传统数据库在应用场景上的区别，掌握简单大数据环境的搭建方法（层次：理解 + 掌握）
> **教材对应**：单元 11 · 大数据

大数据不是"数据多"这么简单。当数据规模超出单台机器、单一数据库的处理能力时，采集、存储、计算、治理的整套方法都必须改变，这才产生了大数据技术体系。本节的重点是把"4V 特征—分层架构—Hadoop 生态—与传统数据库的分工"串成一条线，并动手搭起一个能跑起来的最小环境。

## 一、大数据的概念、结构类型与核心特征

### 1. 基本概念

大数据指规模巨大、类型多样、产生速度快，无法用常规软件工具在合理时间内采集、存储、管理和分析的数据集合，以及与之配套的技术体系。它包含两层含义：一层是**数据本身**的特征，另一层是**处理这些数据所需的新技术、新架构**。考试问"大数据是技术还是数据"，准确回答是二者兼指。

### 2. 结构类型

| 类型 | 特征 | 典型例子 | 处理方式 |
|---|---|---|---|
| 结构化数据 | 有固定模式，可用二维表表示 | 关系数据库中的订单、成绩表 | SQL、数据仓库 |
| 半结构化数据 | 有一定结构但模式不固定，自带标记 | JSON、XML、日志、网页 | 解析后处理，NoSQL |
| 非结构化数据 | 无预定义模式 | 图像、音频、视频、文档 | 特征提取、深度学习 |

三类数据中，非结构化数据占比最高且增长最快，这正是传统关系数据库力不从心的原因。

### 3. 核心特征

业界用 4V 概括大数据的核心特征，后又补充真实性形成 5V。

| 特征 | 英文 | 含义 | 带来的挑战 |
|---|---|---|---|
| 大量 | Volume | 数据规模从 TB 级升至 PB、EB 级 | 单机存不下，需分布式存储 |
| 多样 | Variety | 结构化、半结构化、非结构化并存 | 需多种模型与统一管理 |
| 高速 | Velocity | 数据产生快、要求处理及时 | 需流式计算与实时响应 |
| 低价值密度 | Value | 单条数据价值低，整体价值高 | 需全量分析才能提炼价值 |
| 真实性 | Veracity | 数据存在噪声、缺失与失真 | 需数据清洗与质量治理 |

**例 6.4-1** 某电商平台每天产生数十亿条点击、下单、支付记录，其中既有数据库中的订单表，也有商品图片与客服录音；运营部门希望当天就能看到转化率看板。请指出这体现了大数据的哪些特征。

**解**

1. 数十亿条记录、需长期留存，体现"大量"（Volume）。
2. 订单表是结构化数据，图片属非结构化、日志属半结构化，体现"多样"（Variety）。
3. 数据持续高速产生，且要求当天出结果，体现"高速"（Velocity）。
4. 单条点击记录几乎没有分析价值，需聚合全量才能算出转化率，体现"低价值密度"（Value）。
5. 点击记录中存在误点、爬虫流量，需清洗后才可用，体现"真实性"（Veracity）。

- **易错点**：①把"数据量大"当作大数据的唯一特征，忽略多样与高速；②把"价值密度低"误解为"没有价值"，实际是总量价值高；③把 4V 中的 Value 写成"价值高"，其准确表述是价值密度低。

## 二、时代背景、应用场景与发展趋势

### 1. 时代背景

大数据兴起有四个支撑条件：移动互联网与物联网使数据来源空前丰富，传感设备把物理世界持续数字化；存储介质成本大幅下降，使"先存下来再说"成为可能；分布式计算与集群算力使 PB 级处理可行；机器学习算法成熟，使数据能转化为预测与决策。四者缺一不可，因此大数据是技术、成本与需求共同推动的结果。

### 2. 应用场景

| 领域 | 典型应用 | 主要数据与价值 |
|---|---|---|
| 电商零售 | 个性化推荐、动态定价、库存预测 | 浏览与交易日志，提升转化率 |
| 交通出行 | 路况预测、信号配时、路径规划 | 卡口与轨迹数据，缓解拥堵 |
| 金融 | 信用评分、反欺诈、智能投顾 | 交易与行为数据，控制风险 |
| 医疗健康 | 疾病预测、影像辅助诊断、医保控费 | 病历与影像数据，提升诊疗效率 |
| 政务 | 一网通办、城市运行监测 | 多部门共享数据，提升治理能力 |
| 工业 | 设备预测性维护、质量追溯 | 传感器时序数据，降低停机 |

### 3. 发展趋势

一是**实时化**，从离线批处理转向流式计算，风控与推荐要求秒级响应；二是**智能化**，大数据与人工智能深度融合，数据是模型训练的原料；三是**云原生化**，存算分离、弹性伸缩成为主流部署方式；四是**治理规范化**，数据确权、质量、安全与隐私保护日益重要，隐私计算让"数据可用不可见"；五是**数据要素化**，数据被作为生产要素参与流通与分配。

## 三、大数据系统架构

### 1. 分层架构

大数据系统通常按数据流向分为五层，每层解决一类问题。

| 层次 | 主要职责 | 代表技术 |
|---|---|---|
| 数据采集层 | 从业务库、日志、消息、传感器获取数据 | Flume（日志）、Sqoop（关系库）、Kafka（消息）、爬虫 |
| 数据存储层 | 分布式可靠存储海量数据 | HDFS（文件）、HBase（列式）、对象存储 |
| 计算处理层 | 批处理、流处理与资源调度 | MapReduce、Spark、Flink、YARN |
| 分析挖掘层 | 数据仓库建模、统计分析与机器学习 | Hive、Spark SQL、MLlib |
| 治理应用层 | 元数据、质量、安全、可视化与服务输出 | 数据目录、质量平台、BI 工具 |

理解架构的关键是分清"存"与"算"：HDFS 负责把数据切块多副本存放在多台机器上，YARN 负责把计算任务分配到有空闲资源的机器上，MapReduce、Spark、Flink 则是不同风格的计算引擎。

### 2. Hadoop 生态

Hadoop 是最经典的大数据基础平台，其核心是 HDFS、MapReduce 与 YARN，周边形成完整生态。

| 组件 | 作用 |
|---|---|
| HDFS | 分布式文件系统，数据切块多副本存储，适合一次写入多次读取 |
| MapReduce | 批处理计算模型，"分而治之"后汇总 |
| YARN | 集群资源管理与任务调度 |
| Hive | 把 SQL 转换为分布式作业，构建数据仓库 |
| HBase | 基于 HDFS 的列式 NoSQL 数据库，支持随机读写 |
| Spark | 基于内存的计算引擎，比 MapReduce 快，支持批流一体 |
| Flink | 以流处理为核心的引擎，低延迟、支持事件时间 |
| Sqoop / Flume / Kafka | 分别负责关系库导入导出、日志采集、消息缓冲 |

HDFS 的短板要记牢：不适合存储大量小文件（元数据占用大）、不适合低延迟随机写、不适合频繁修改文件。因此需要随机读写的场景改用 HBase。

**例 6.4-2** 某网站要把每天产生的访问日志留存下来做离线统计，同时还要对异常访问在秒级内告警。请给出技术选型。

**解**

1. 采集：日志由各服务器持续产生，用 Flume 采集并汇聚；同时把日志写入 Kafka 做缓冲，避免下游故障时丢数据。
2. 离线链路：Kafka 中的数据落地到 HDFS 长期存储，用 Hive 建外部表，以 SQL 完成日活、留存等统计，结果导出到报表库。
3. 实时链路：由 Flink 直接消费 Kafka，按窗口统计单位时间的访问频次，超过阈值即触发告警。
4. 两条链路共用同一份数据源，即"批流一体"的典型架构：离线保证准确与全量，实时保证时效。

- **易错点**：①把离线统计也放到 Flink 上，忽视批处理在成本与准确性上的优势；②用 HDFS 直接支撑秒级告警，HDFS 面向高吞吐而非低延迟；③认为 Kafka 是数据库，它主要作用是缓冲与解耦。

## 四、与传统数据库的区别及环境搭建

### 1. 应用场景上的区别

| 维度 | 传统关系数据库 | 大数据平台 |
|---|---|---|
| 数据规模 | GB 至 TB 级 | TB 至 PB 级以上 |
| 数据类型 | 以结构化为主 | 结构化、半结构化、非结构化 |
| 模式约束 | 写时模式，先定义表结构 | 读时模式，先存后解析 |
| 事务特性 | 强调 ACID 强一致 | 多为 BASE，最终一致 |
| 扩展方式 | 纵向扩展，提升单机配置 | 横向扩展，增加普通节点 |
| 典型负载 | OLTP，高频小事务增删改查 | OLAP，海量数据批量分析 |
| 响应要求 | 毫秒级点查 | 秒至分钟级全量扫描 |

两者不是替代关系而是分工关系：业务系统用关系数据库保证事务与一致性，分析系统把数据同步到大数据平台做全量分析，形成"OLTP 管交易、OLAP 管分析"的格局。

### 2. 简单大数据环境的搭建

以 Hadoop 伪分布式为例，在一台 Linux 虚拟机上即可完成，步骤如下。

1. **准备环境**：安装 Linux 虚拟机，配置主机名与静态 IP，关闭或放行防火墙端口，安装 JDK 并配置 `JAVA_HOME`。
2. **安装 Hadoop**：解压安装包到指定目录，在环境变量中配置 `HADOOP_HOME` 与 `PATH`。
3. **配置核心参数**：在 `core-site.xml` 中设置 `fs.defaultFS` 为 `hdfs://localhost:9000`，指明文件系统地址；在 `hdfs-site.xml` 中设置副本数 `dfs.replication` 为 1（单机无需多副本）。
4. **配置计算框架**：在 `mapred-site.xml` 中指定 `mapreduce.framework.name` 为 `yarn`，在 `yarn-site.xml` 中配置资源管理器地址与节点管理器辅助服务。
5. **配置免密登录**：生成密钥并写入本机授权文件，使启动脚本无需反复输入口令。
6. **格式化与启动**：首次运行 `hdfs namenode -format` 初始化元数据，再执行 `start-dfs.sh` 与 `start-yarn.sh` 启动集群。
7. **验证**：用 `jps` 查看进程，应出现 NameNode、DataNode、SecondaryNameNode、ResourceManager、NodeManager；浏览器访问 9870 端口可查看 HDFS 状态；用 `hdfs dfs -mkdir` 与 `-put` 上传文件验证读写。

**例 6.4-3** 某同学搭建伪分布式环境后执行 `jps`，只看到 Jps 一个进程；查看日志发现 DataNode 启动失败并提示与 NameNode 的集群标识不一致。最可能的原因和解决办法是（　）。

A. JDK 未安装，应重装 JDK
B. 多次执行了 `hdfs namenode -format`，导致元数据集群标识与 DataNode 不一致，应清理数据目录后重新格式化并启动
C. 副本数设置为 1，应改为 3
D. 未配置 YARN，应补配 `yarn-site.xml`

**解**

1. 现象是 DataNode 未能启动，且日志明确指出集群标识不一致，指向元数据与数据目录不匹配。
2. 该问题常见于重复格式化：每次格式化会生成新的集群标识，而旧数据目录仍保留旧标识，DataNode 拒绝加入。
3. 处理办法是停止服务，删除各节点数据目录与元数据目录后只格式化一次，再启动并用 `jps` 验证。
4. JDK 未装会导致所有组件都起不来，与日志提示不符；副本数在单机设为 1 是正确做法；YARN 未配置不影响 DataNode 启动。答案选 B。

- **易错点**：①反复格式化，认为"多格几次更干净"；②把副本数在单机环境设为 3，导致副本不足报警；③只看进程数量不看日志，凭猜测改配置。

## 本节小结

1. 大数据既指规模巨大、类型多样、产生快速的数据集合，也指处理这些数据的技术体系。
2. 数据按结构分为结构化、半结构化、非结构化三类，非结构化占比最高、增长最快。
3. 核心特征是 4V：大量、多样、高速、低价值密度；补充真实性后为 5V。
4. 大数据系统分采集、存储、计算、分析、治理应用五层；Hadoop 核心为 HDFS、MapReduce、YARN，Hive 做数仓、HBase 支持随机读写、Spark 内存计算、Flink 流处理。
5. 与传统数据库的分工是 OLTP 与 OLAP：前者管交易与强一致，后者管海量分析。
6. 伪分布式搭建的关键步骤是装 JDK、配四个配置文件、配免密、格式化一次、启动并用 jps 与 9870 端口验证。

A. 前者做 OLAP，后者做 OLTP
B. 前者做 OLTP 保证事务一致，后者做 OLAP 支撑海量分析
C. 两者功能完全相同，可以互相替代
D. 前者只能存文本，后者只能存图片

7.（单选）Hadoop 伪分布式环境搭建中，首次启动前必须执行的操作是
A. 把副本数设为 3
B. 执行 `hdfs namenode -format` 初始化元数据
C. 安装 HBase
D. 配置多台物理机

8.（多选）下列关于大数据平台各组件的表述，正确的有
A. Flume 常用于采集日志数据
B. Sqoop 用于关系数据库与 HDFS 之间批量导入导出
C. Kafka 可作消息缓冲，实现数据采集与处理的解耦
D. HDFS 最适合支撑毫秒级随机读写的事务场景

### 参考答案

1. **D**。4V 为 Volume、Variety、Velocity、Value；Virtualization 指虚拟化，不是大数据特征。
2. **B**。JSON、XML 自带标记但模式不固定，日志有格式而无严格表结构，均属半结构化。
3. **C**。HDFS 面向高吞吐，一次写入多次读取、多副本容错；不适合小文件、低延迟随机写，也不限于结构化数据。
4. **B**。YARN 负责资源管理与调度；HDFS 管存储，Hive 管 SQL 转换，HBase 是列式数据库。
5. **A**。Hive 把 SQL 转成分布式作业；Flink 是流计算引擎，Sqoop 负责数据导入导出，ZooKeeper 负责协调。
6. **B**。关系数据库承担 OLTP，大数据平台承担 OLAP，二者分工互补而非互相替代。
7. **B**。首次启动前需格式化元数据；副本数单机应为 1，HBase 与多机并非必需。
8. **ABC**。D 错：HDFS 面向高吞吐批处理，不适合毫秒级随机读写，此类需求应由 HBase 等承担。
